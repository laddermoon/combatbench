# Reclip 功能概念与方案（设计稿）

> 状态：评审通过的目标设计；下文不代表当前代码已全部实现。
>
> 标注约定：
> - **[原始构想]**：来自需求方的设计意图。
> - **[新增建议]**：评审时补充的修改/细化，需重点 Review。
> - **[使用建议]**：面向工具用户的用法建议。

## 1. 目标定位

Reclip 的任务是：基于一个源 Clip，生成一个新的 CoreClip，并且这个新 Clip：

1. 保留用户需要的动作语义；
2. 每一帧状态都来自真实仿真；
3. 记录真实产生的速度、接触和姿态；
4. 携带可执行的 `ref_action`，满足

   ```text
   sim(output_clip[k], ref_action[k]) == output_clip[k+1]
   ```

   在相同仿真配置和数值误差范围内成立。

它不是“把源姿态插值一遍”，也不是“给源轨迹配一个参考动作”；它是把源轨迹表达的运动意图，通过动力学优化**投影到可执行运动空间**。

**[原始构想，未验证]** Reclip 得到的轨迹还可以直接用于模仿学习，加速策略学习。例如机器人要实现“从某个状态到打击状态”的动作，可以先用 Reclip 得到一个动力学上可行的参考解，再让策略直接模仿这个可行解。该方案目前尚未通过训练实验验证。

**[现状]** 当前 `reclip` 已验证：给定离散导轨和动作序列优化器，逐 50ms 执行仿真，将实际落点写入输出 Clip；因此输出动作序列对输出状态序列是自洽的。已验证的求解路线包括 greedy、MPC 和 sweep，其中 sweep（迭代射击/后缀评分）在短打击动作上效果最好。

## 2. 三个核心对象

### 2.1 源 Clip

源 Clip 是输入动作描述。其离散帧里最重要的是**姿态序列**：

- 每帧姿态：`root_pos`、`root_rot`、`joint_pos_norm`；
- 起始帧和末帧需要完整状态，尤其是速度；
- 中间帧速度在当前设计中不作为优化目标，也没有独立价值；它可以保留在源 Clip 中供诊断，但不参与 Reclip 目标构建或评分。

**[原始构想]** Reclip 不把中间帧速度当作需要复刻的目标。即使是保留源时间线的 `track`，时间线约束的也是姿态序列；速度只用于描述从某一时刻状态向目标点运动的牵引/趋势，不单独计分。需要匹配速度的只有末端帧，而且是否匹配由目标类型决定。

因此默认：

- 初始速度：使用源 Clip 的真实初始速度，因为它属于完整仿真初始状态；
- 中间帧速度：不作为目标；输出中的中间速度是求解产生的实际结果，不是要复现的数据；
- 末端速度：是否匹配由目标类型决定；
- 输出速度：永远来自仿真实际测量，不从输出姿态二次差分伪造。

### 2.2 目标路径（Target Path）

**[原始构想]** 对忽略源时间线的目标，需要把源 Clip 表示成一条连续轨迹；Reclip 后，机器人可以沿该轨迹单调前进。

**[已接受建议]** 为了明确语义，把“轨迹”拆成“路径”和“时间进度”：

```text
姿态路径：      q = γ(s),  s ∈ [0, 1 + s_ext],  0 < s_ext << 1
时间进度：      s = s(t)
带时间的目标：  q_target(t) = γ(s(t))
```

其中 `s=1` 对应源 Clip 的目标末姿态；`s` 可以少量超过 1，用于表达“通过目标姿态后继续前进”。外延范围 `s_ext` 是有界参数，不应当很大。

- `γ(s)` 只定义身体各部分如何协调变化；
- `s(t)` 定义机器人沿路径推进的时间和速度；
- 两者组合后才是一条带时间的目标轨迹。

目标路径只包含姿态，不直接包含速度：

- 根位置：连续位置路径；
- 根朝向：旋转空间中的连续插值；
- 关节姿态：归一化关节空间中的连续路径。

如果需要由路径给出运动趋势或末端边界，可由路径导数和进度速度生成参考方向：

```text
dq_target/dt = dγ/ds · ds/dt
```

它用于描述“朝目标路径前方运动”的牵引关系，不是中间帧速度匹配目标。根朝向不能用普通向量差直接求导，需要在旋转空间中计算角速度，再转换为 CoreClip 的机体系角速度字段。

### 2.3 输出 Clip

输出仍是标准 CoreClip：

- 固定 20Hz 控制帧；
- 每帧状态来自仿真；
- `ref_action[k]` 是导致输出 `state[k] -> state[k+1]` 的动作；
- meta 记录源 Clip、路径构建方式、目标类型、进度、完成状态和优化参数。

**[原始构想]** Humanoid21 的 `set_core_state` 由仿真器实现保证可以完整加载仿真状态，因此优化器可以从保存的 CoreState 恢复中间状态并继续 rollout；输出 Clip 也可以直接记录这些仿真落点。

**[已接受建议]** 尽管中间状态可完整恢复，最终仍应从初始状态完整回放一次选中的动作序列并重新录制输出。这不是为了弥补状态恢复能力不足，而是为了得到一条连续、统一的最终轨迹和明确的可执行性验证结果。

## 3. 四类优化目标

### 3.1 目标对照表

| 目标 | 建议名称 | 是否保留源时间线 | 中间目标 | 完成定义 |
|---|---|---:|---|---|
| 1 | `track` | 是 | 同步复刻每帧姿态（中间速度不作目标） | 完成源时长，报告整段姿态跟踪误差 |
| 2 | `reach-state` | 否 | 沿路径单调前进 | 路径进度到达 1，报告末姿态和末速度误差（暂不实现） |
| 3 | `reach-stop` | 否 | 沿路径单调前进，允许提前制动 | 路径进度到达 1，末速度尽量接近零并报告误差 |
| 4 | `pass` | 否 | 沿路径单调前进 | 正向通过末姿态邻域，末速度自由 |

### 3.2 `track`：复刻目标轨迹

**[原始构想]** 尽量复刻源 Clip 每一帧的姿态和速度，并保持进度同步。

实现语义：

- `s(t)` 基本等于源 Clip 原始进度；
- 每个输出控制帧有对应的源目标时间点；
- 目标包含同步姿态；中间帧速度不作为匹配目标；
- 重点是整段动作外观、节奏和动态过程，而不只是末帧。

适用场景：retarget Clip 重规范化、动作修复、把有速度/接触问题的 Clip 转成物理可执行版本。

### 3.3 `reach-state`：最速到达目标姿态并保留末态速度（暂不实现）

**[原始构想]** 忽略源轨迹时间线，但保留目标点速度；机器人应以尽可能短的时间到达末姿态，同时末速度尽量接近源末速度。

**[原始构想，修订]** 当前定义仍以路径进度为主轴：当 `s` 到达 1 时，认为路径终点已经到达。此时不设置硬性的姿态/速度通过容差，而是反馈：

```text
s(t_goal) = 1
report: pose_error(q(t_goal), q_end)
report: vel_error(v(t_goal), v_end)
```

初步优化思路是先让机器人沿轨迹尽可能快地推进，再在接近末端的阶段尽量匹配末速度。由于优化能力和动力学可行性无法保证达到固定容差，速度匹配目前是软性目标，而不是硬完成条件。

**[实现计划]** 该目标仅为语义完整性保留，暂不进入当前实现计划；先实现 `track`、`pass`，以及后续 `reach-stop`。

### 3.4 `reach-stop`：最速到达目标姿态并静止

**[原始构想]** 忽略源末速度，以最快速度到达目标姿态并尽量停止。

完成主轴仍是路径进度：当 `s` 到达 1 时认为路径终点已经到达，并报告：

```text
s(t_goal) = 1
report: pose_error(q(t_goal), q_end)
report: vel_error(v(t_goal), 0)
```

**[原始构想]** 不额外加入“保持一段时间不倒”的验证。Reclip 当前主要解决短连续动作的生成问题，不为复杂失稳/恢复场景增加优化目标或判据。

### 3.5 `pass`：最速通过目标姿态

**[原始构想]** 机器人以最快方式通过目标姿态，允许经过目标后继续前进；末速度不受限。

完成条件：

```text
存在 t_pass：
    q(t_pass) 进入末姿态邻域
    且路径进度沿正方向通过 s_end
```

**[原始构想]** `pass` 只关心是否沿路径正向通过目标姿态：

- 不要求目标姿态本身是稳定状态；
- 不要求通过后的机器人保持稳定，也不做通过后 rollout 验证；
- 默认不要求速度；如果以后需要“通过时拳速不低于某值”，应作为额外约束，而不是混进默认目标；
- 第一版按 20Hz 控制帧判断通过事件，不做物理子步插值检测。

## 4. 目标路径的构建

### 4.1 `endpoints`：只取两端

**[原始构想]** 只取首末姿态构建连续目标路径；不适配 `track`。

适用：单向短过渡，例如站姿到伸展拳姿。优点是简单、路径约束少、动力学有更大自由度。

**[使用建议]** 对首末姿态接近、但中间有出拳/踢腿往返形态的 Clip，`endpoints` 会丢失动作语义，不应使用。

### 4.2 `all`：全部源姿态作为有序约束点

**[原始构想]** 保留源 Clip 的全部姿态，相当于在中间加入轨迹约束点，可适配全部目标。

适用：需要保留动作时序形态、蓄力/爆发节奏、非单调动作的 Clip。

**[原始构想，修订]** `all` 允许实际运动在路径附近通过，而不是强迫每一帧精确穿过插值点；否则源 Clip 的几何误差、穿地或不可保持姿态会被原样带入优化。这里不规定固定容差：允许多大偏离由优化器能力和目标取向决定，最终只报告路径偏差。

### 4.3 插值建议

**[已接受建议]** 第一版建议使用受控分段三次插值：

- 根位置、关节姿态：分段三次曲线，尽量平滑但约束过冲；
- 根朝向：旋转空间中的插值，不能直接对四元数四个分量做普通三次插值；
- 路径参数 `s`：对目标 2/3/4，按加权姿态距离或近似弧长参数化，不按源帧索引线性参数化；
- 对 `track`：保留源时间点到路径参数的映射。

这样“采样密集”不会错误地表示“应该花更多时间”，因为源时间线已经由 `s(t)` 单独表达。

### 4.4 路径投影与局部偏离

**[已接受建议]** 对仿真状态 `q_k`，需要找到其当前路径进度 `s_k`：

```text
s_k = argmin_s pose_distance(q_k, γ(s))
```

但全局搜索容易在路径自交或姿态重复时跳到后面相似姿态，因此投影应：

- 以上一帧 `s_{k-1}` 为先验；
- 只在局部窗口 `[s_prev, s_prev + ds_max]` 内搜索；
- 强制 `s_k >= s_{k-1}` 满足单调进度；
- 记录路径偏差，但不预设固定“路径走廊”容差；允许多大偏离由优化器决定。

“单调前进”约束的是统一进度 `s`，不是每个关节都单调。路径本身可以包含先收后放、转腰再回正等协调动作。

#### 根位置目标模式

`TargetPath` 的姿态距离始终计算 `jp` / `rp` / `rq` 三个诊断分量，但可通过 `root_pos_mode` 决定 `rp` 是否进入加权总分：

- `absolute`：默认模式；绝对根位置参与路径参数化、投影、路径误差和 terminal pose error；
- `free`：`rp=0`；路径仍记录和插值 `root_pos`，但进度只由 `root_rot + joint_pos_norm` 决定。`rp` 原始误差仍作为 component 保留，便于诊断水平/高度漂移。

`free` 适用于 `pass` 和 `reach-stop`，用于“身体姿态到达目标、但不要求回到固定世界坐标”的任务。`track` 必须保持 `absolute`，否则同步复刻目标的语义不完整。

`free` 是**完全忽略绝对根位置**，包括 x/y/z。它不是 init-frame relative position：如果后续需要“保留从初始状态出发的相对位移”或“只忽略 x/y、保留 z”，应增加独立的 relative/free-xy 模式，而不是复用 `free`。

API / CLI 形式：

```python
TargetPath.from_pose_pair(start, end, root_pos_mode="free")
```

```bash
clip reclip ... --objective pass --root-pos-mode free
```

`pose_weights` 仍可用于调 `jp` / `rp` / `rq` 权重；`root_pos_mode="free"` 会固定 `rp=0` 并拒绝非零 `rp` override。`track + free` 由 evaluator 和 CLI 显式拒绝。

### 4.5 路径外延

**[原始构想]** `pass` 目标中，机器人可以“走过终点”，目标路径需要支持外延。

**[已接受建议]** `s` 定义域扩展为 `[0, 1 + s_ext]`，允许超过 1，但只能少量超过。外延应有界，不能无限线性延长导致超出关节范围或破坏支撑。第一版可支持：

- 沿末端切线外延一小段；
- 或由用户提供后续姿态/后续 Clip 作为自然外延。

## 5. 速度边界与运动牵引

源 Clip 的首尾速度具有边界状态语义：

- 初始状态必须包含初始速度，否则仿真起点不完整；
- `track` 通过同步姿态时间点和当前速度自然产生运动牵引，不设置中间速度匹配目标；
- `reach-state` 将源末速度作为软性末端参考并报告误差；该目标暂不实现；
- `reach-stop` 将零速度作为末端参考并报告误差；
- `pass` 不约束末速度。

**[已接受建议]** 首尾速度不一定与路径端点切线同向。仅改变 `ds/dt` 只能改变沿路径方向的速度大小，不能改变速度方向。因此第一版需要处理三种情况：

1. 速度大致沿路径切线：直接使用；
2. 速度偏离切线但可短距离修正：允许路径附近的进入过渡；
3. 速度与目标几何严重冲突：报告边界冲突，不静默修改源速度。

## 6. 优化问题定义

### 6.1 决策变量

主要优化变量是动作序列：

```text
a[0], a[1], ..., a[N-1],  a[k] ∈ [-1, 1]^21
```

以及由动作序列隐含产生的：

- 路径进度 `s_k`；
- 完成时间 `t_goal`；
- 每帧路径偏差；
- 终止条件满足情况。

**[已接受建议]** 第一版不直接优化连续时间 `t`，而是在固定控制步长下优化动作序列，并用不同时间预算或多组搜索求较短完成时间。这样与现有 20Hz 控制接口和 sweep 求解器兼容。

### 6.2 评分组成

目标评分应由以下几部分组成：

```text
J = -w_progress · 进度收益
    + w_path     · 路径偏差
    + w_terminal · 终端条件误差
    + w_vel      · 末端/边界速度误差（仅目标要求时）
    + w_reg      · 动作正则
    + w_fall     · 可选的跌倒/失稳惩罚（不作为目标状态的稳定性要求）
```

各目标侧重不同：

- `track`：同步时间点的姿态误差为主；
- `reach-state`：进度收益 + 末端姿态误差 + 末端速度误差（后段软性目标，暂不实现）；
- `reach-stop`：进度收益 + 末端姿态误差 + 零速度误差；
- `pass`：通过时间 + 路径偏差，末速度不计入终端误差。

**[已接受建议]** 综合评分只用于优化排序；最终“是否更快”必须按明确指标报告，例如首次满足条件的物理时间、路径偏差、末速度误差和完整回放误差，不能只拿综合分说更快。

### 6.3 不建议逐帧纯贪心

**[原始构想]** 每一步可以选择“沿轨迹走得最远”的 action。

这个方向是合理的：它把目标从“贴近固定时刻的导轨”改成“沿路径推进最多”。但如果每个 action 只看一步收益，会产生风险：

- 容易移动的部位先完成，留下难调整的部分慢慢收敛；
- 当前更靠近目标姿态，不代表剩余到达时间更短；
- 某些动作先积累有利速度，单帧评分看不出来；
- 可能出现维度/部位间步调不协调。

**[已接受建议]** 保留“走得越远越好”的目标，但评价 action 时应看它对**后续一段或整个后缀轨迹**的影响，而不是只看下一步落点。也就是：

```text
候选 action -> 执行后续候选序列 -> 看整段路径进度/完成时间/路径偏差
```

这正好复用当前已验证的 sweep/iterated-shooting 思路：当前动作的价值由完整 rollout 结果决定。

## 7. 求解器方案

### 7.1 第一版主求解器：路径版 sweep

**[现状]** 现有 `reclip_sweep` 以初始动作序列为起点，对每个动作按“执行该动作后，当前后缀序列造成的总误差”评分，已在 extend 打击 Clip 上明显优于逐帧 greedy 和当时的短窗口 MPC。

**[已接受建议]** 新版本保留这个框架，但把“固定帧号导轨误差”替换为“连续路径评分”：

1. 初始化动作序列；
2. 从初始状态 rollout；
3. 对落点做路径投影，得到进度和偏差；
4. 逐帧尝试候选动作；
5. 用完整后缀 rollout 的结果更新动作；
6. 多轮 sweep 后输出最终 rollout。

这样能把当前已验证的能力直接迁移到新目标。

### 7.2 时间搜索

**[已接受建议]** 第一版不承诺数学全局最速。可先实现“给定时间预算下尽量完成”，再进行多预算搜索：

- 对若干时间预算运行优化；
- 记录每个预算是否满足完成条件；
- 以上一次成功的动作序列/进度结果热启动下一次；
- 使用多个 seed / 初值避免一次失败误判不可达。

不建议简单把一次优化失败当作“该时长物理不可达”，因此也不建议直接用单次结果做严格二分。更合适的说法是：

> 在给定路径、容差、预算和求解器限制下，搜索到的较短完成时间。

### 7.3 初始化来源

候选初始化：

- 源 Clip 的 `ref_action`（如果有）；
- 目标路径姿态转换出的 PD 目标；
- 之前成功时间预算的动作序列；
- 多个随机 seed / 扰动序列。

**[已接受建议]** 对 `track + all`，源 `ref_action` 通常是最好的热启动；对 `pass + endpoints`，路径 PD 目标和多 seed 更重要。

## 8. 完成判定与事件检测

### 8.1 姿态偏差

不建议只使用一个全身平均误差；应分开报告，但不预设固定容差。允许或要求多大偏差由优化器/调用方决定：

- 根位置误差；
- 根朝向误差；
- 关节姿态误差；
- 可选关键部位误差（拳、脚、躯干）。

这避免“某些部位到了、另一些没到位，但平均值看起来可以接受”。

### 8.2 速度偏差

按目标决定是否参与评分或只报告；当前设计不设置中间帧速度误差：

- `track`：只检查同步姿态；末端速度是否作为完成条件由调用方另行指定；
- `reach-state`：报告末端速度误差，但不设硬完成阈值；该目标暂不实现；
- `reach-stop`：报告末端零速度误差，不额外做保持验证；
- `pass`：默认无末端速度约束。

### 8.3 通过事件记录

**[原始构想]** 第一版按 20Hz 控制帧判断通过事件，不做物理子步插值检测。若动作在两个控制帧之间短暂进入目标邻域，当前定义不额外补判；后续如需更高精度，可以再加入子步事件检测，但不是当前实现计划。

meta 记录事件发生时的控制帧及其对应的 Clip 时间，例如：

```json
"event": {"type": "pass", "time": 0.35, "frame": 7}
```

## 9. 输出与验证

### 9.1 输出 Clip 的可执行性

最终 Clip 必须满足：

```text
sim(output_clip[k], ref_action[k]) -> output_clip[k+1]
```

这是由生成方式保证的，但应增加完整回放验证：

1. 从输出 Clip 第 0 帧开始；
2. 依次执行保存的 `ref_action`；
3. 比较实际落点与输出 Clip 状态；
4. 检查关节姿态、根位姿和速度，而不只检查关节误差。

**[已接受建议]** 当前验证重点偏关节误差，新版本应把根位置、根朝向、根速度和关节速度都纳入回放误差报告。

### 9.2 结果状态

优化结果不能只输出一个 final_D。建议至少包含：

```jsonc
{
  "objective": "pass",
  "path": {"mode": "endpoints", "length": 1.0},
  "status": "completed | budget_exhausted | failed",
  "event": {"type": "pass", "time": 0.374},
  "tolerances": {"pose": ..., "vel": ...},
  "metrics": {
    "path_error_mean": ...,
    "path_error_max": ...,
    "terminal_pose_error": ...,
    "terminal_vel_error": ...,
    "replay_error": ...
  },
  "solver": {"method": "path_sweep", "sweeps": ..., "seed": ...},
  "note": "fastest time found under this solver/budget; not a global minimum-time proof"
}
```

`budget_exhausted` 表示“搜索预算耗尽，没有找到满足条件的解”，不能写成“物理不可达”。

### 9.3 血缘

输出 meta 应继承源 Clip 的 lineage，并追加：

- 源 Clip / 源帧范围；
- 路径构建方式；
- 目标类型；
- 时间预算和完成时间；
- 优化参数；
- 验证指标。

## 11. 建议推进顺序

### 阶段 1：统一抽象并保持现有能力

- 新增 `TargetPath`：`endpoints` / `all`；
- 支持姿态查询、路径导数、局部进度投影；
- 把当前固定时间线的 `track + all` 迁移到新抽象；
- 用现有 extend Clip 回归，确认不比当前 `via` reclip 退化。

### 阶段 2：先实现 `pass + endpoints`

这是最贴近“短单向出拳”需求的组合：

- 固定时间预算；
- 沿路径推进评分；
- 路径偏差评分（不预设固定容差）；
- 按控制帧判断通过事件；
- 输出完整可执行 Clip 和视频。

### 阶段 3：实现 `pass + all` 与时间搜索

- 保留源姿态约束点和路径参数映射；
- 引入多个时间预算、热启动、多 seed；
- 报告搜索得到的最短通过时间；
- 对比 `endpoints` 与 `all`：前者更自由，后者更保留动作形态。

### 阶段 4：补齐 `reach-stop`

- `reach-stop`：末端零速度误差；
- 边界速度冲突检测；
- 多预算时间搜索；
- `reach-state` 暂不实现，仅在目标和接口设计中保留语义占位。

### 阶段 5：统一 CLI / 报告 / 测试

建议接口（未实现）：

```bash
PYTHONPATH=. python3 -m mocap.humanoid21.clip reclip \
    --clip source.npz \
    --objective track|reach-state|reach-stop|pass \
    --path endpoints|all \
    --time-budget 0.60 \
    [--tol-pose ... --tol-vel ...] \
    [--method sweep --sweeps 3 --seed 0] \
    --out result.npz
```

可保留当前 `--start/--end/--via` 形式作为兼容层，但内部统一映射到“源 Clip + 目标 + 路径”。

## 12. 已接受的补充决策

以下内容不是原始构想的一部分，现已全部接受：

1. **“目标轨迹”拆成路径 `γ(s)` 和时间进度 `s(t)`。**  
   好处是四种目标共用路径，时间线由目标决定。

2. **中间帧速度不作为优化目标。**
   它既不是 `track` 的匹配项，也不由路径导数生成后单独计分；实际中间速度是求解结果的一部分。末端速度是否匹配由目标类型决定。

3. **路径投影只允许局部、单调推进。**  
   好处是避免跳到路径后面的相似姿态；代价是可能无法处理需要临时回退的动作。

4. **实际运动允许偏离路径约束点，偏离程度由优化器决定（已确认）。**
   设计不预设固定路径容差；最终通过路径偏差指标观察实际跟随质量。

5. **评价 action 时看完整后缀 rollout，而不是只看一步推进。**  
   好处是保留跨帧动量/协调；代价是计算成本更高。

6. **`pass` 不做子步事件检测或通过后稳定性验证（已确认）；路径外延为 `s` 少量超过 1。**
   目标姿态本身可以是失稳状态；当前只按控制帧判断是否沿路径正向通过。

7. **`reach-stop` 不做额外保持验证（已确认）。**
   Reclip 当前面向短连续动作生成，不针对复杂失稳/恢复场景增加优化目标或判据；末端只报告零速度误差。

8. **“最快”只承诺求解器和预算下找到的最短时间。**  
   好处是语义诚实；代价是不能宣称全局时间最优。

9. **最终输出从初始状态完整回放一次并重新录制（已确认必要）。**
   这不是因为 `set_core_state` 不完整——仿真器已保证其完整加载——而是为了统一生成最终轨迹，并把完整回放误差作为明确的验证指标；代价是额外一次完整仿真。

10. **`track` 只把同步姿态作为目标，不新增中间速度配置。**
    中间速度只描述求解产生的实际运动趋势；若调用方需要末端速度匹配，应使用对应的末端条件，而不是扩展逐帧速度误差。
