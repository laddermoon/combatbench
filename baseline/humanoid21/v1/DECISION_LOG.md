## D1 — 第一阶段技能指令编码：6 维脚手分解码（v0，非最终方案）

**日期**：2026-11-16 ｜ **状态**：已采纳（v0）

**背景**：`bootstrip.md` 问题一。策略输入 = 本体观测 + 技能信息，不含对手信息。
原设想是二进制形式的"脚步动作编码 + 脚步参数 + 手部动作编码 + 手部参数"，
待评估点是不同技能间能否共享能力、互不打架。

**决策**：第一阶段采用 6 维技能指令，脚手两组各 3 维：

| 字段 | 取值 | 语义 |
|---|---|---|
| `step_enable` | 0 / 1 | 是否要求本步完成一次前迈 |
| `step_side` | +1 左 / −1 右 | 迈出的脚 |
| `step_size` | −1 小 / 0 中 / +1 大 | 步幅档（预留，当前固定 0） |
| `punch_enable` | 0 / 1 | 是否要求本步完成一次直拳 |
| `punch_side` | +1 左 / −1 右 | 出拳手 |
| `punch_height` | −1 低 / 0 中 / +1 高 | 打点高度档（预留，当前固定 0） |

**编码规则**：

- 开关：`0/1`
- 左右侧：`±1`（对称表达，沿用 hierarchy `eff_side` 惯例）
- 有序档位（大小、高低）：**单维三态 `−1/0/+1`**——一维浮点只取三个离散值
  即可表达三档，同时保留"小–中–大"的距离结构
- 无序类别（未来动作类别扩展时）：预留 one-hot，不采用无语义的二进制编号

**约束与说明**：

- 通道关闭时其参数统一置 0（不出拳则 `punch_* = [0,0,0]`），避免无意义参数
  成为输入噪声
- "不要求前迈" ≠ 禁止腿部运动——腿仍参与平衡与发力；是否必须完成一次脚步
  由技能契约与边界定义（`bootstrip.md` 问题五）
- 脚手两组指令可表达组合技能（如"同一步内前迈刺拳"），但组合可用性须单独
  训练与验证，不随单项技能自动成立
- 第一阶段实际变化 4 个技能（左/右前迈 × 左/右直拳），`step_size` /
  `punch_height` 为预留维度
- **本方案明确不是最终协议**：6 维只覆盖"技能选择"部分；"本步上下文"
  （相位、剩余预算、事件信息等，`README.md` §3、`bootstrip.md` 问题五）
  是否进入网络输入、以何种形式进入，待动作边界问题讨论后定稿。注意旧
  hierarchy 实现中移动目标点本身携带了相位信息，固定技能码不含相位——
  不要靠编码方案回避起始/终止态混淆问题
- **已知风险**：技能间能力共享与梯度冲突（步态与出拳共享躯干/重心控制）
  只能靠组合训练与成功率实验检验，编码形式只能缓解不能保证

**第一阶段四技能指令编码**（向量序 = 上表字段序）：

| 技能 | `step_enable` | `step_side` | `step_size` | `punch_enable` | `punch_side` | `punch_height` |
|---|---|---|---|---|---|---|
| 左前迈 | 1 | +1 | 0 | 0 | 0 | 0 |
| 右前迈 | 1 | −1 | 0 | 0 | 0 | 0 |
| 左直拳 | 0 | 0 | 0 | 1 | +1 | 0 |
| 右直拳 | 0 | 0 | 0 | 1 | −1 | 0 |

- `side` 语义：`step_side` = 迈出的脚，`punch_side` = 出拳手；+1 = 左，−1 = 右
- 按通道关闭规则，未启用通道的参数位一律为 0
- 全零 `[0,0,0,0,0,0]` = 无技能指令；其语义（原地保持/自由平衡）待技能契约
  定稿，第一阶段不当作技能训练
- 组合码（如 `[1,−1,0,1,−1,0]` = 右前迈 + 右直拳）语法上合法，但第一阶段
  不训练、不保证可用——组合技能是后续验收项而非初始训练目标

## D2 — 训练起点：hier_s2_balance_s42i_b 最新 checkpoint（u01680）

**日期**：2026-11-16 ｜ **状态**：已采纳

**背景**：`bootstrip.md` 问题七。沿用 hierarchy 课程（站立→迈步→扰动平衡）
先获得平衡与步态先验，再训技能；研发摸索期优先复用已训好的扰动平衡策略。

**决策**：以
`baseline/runs/hier_s2_balance_s42i_b/checkpoints/checkpoint_u01680.pt`
（该 run 最新 checkpoint）作为第一阶段训练的 warm-start。

- 策略类：`StateMixtureBoundedStdTruncatedNormalPolicy`
  （`init_policy_mbs_66d.yaml`），obs_dim=66、action_dim=21、
  hidden_dim=256、num_components=3
- 输入保持 66 维不变：57 维本体观测语义不变 + 原 9 维指令槽位中
  **只用 6 维**承载 D1 技能码，其余 3 维置 0
- v0 约定：技能码放指令块前 6 维（cmd[0:6]），cmd[6:9] = 0；
  槽位分配为可调整的实现细节，在实验配置中固定

**已知限制**：

- 9 维指令槽位的旧语义（vx, vy, w, h, eff_type, eff_side, txyz）与新 6 维
  技能码语义不同——指令块对应的首层权重携带的是旧指令的解释，续训中需要
  重新学习指令块语义；复用的主体是**本体观测通路的表征与平衡/步态控制
  先验**
- 该策略训练分布是连续即时伺服指令，未见过"步边界技能"语义；平衡/步态
  先验可复用，技能语义需新学
- 混合策略（num_components=3）对全新指令分布的响应未经检验——若续训
  初期表现异常，考虑对照"仅迁本体权重"或全新初始化
- 研发验证通过后，按 `bootstrip.md` 问题七做正式重训

## D3 — 第一阶段简化：前序技能链式起点池 + 整段结果评分

**日期**：2026-11-16 ｜ **状态**：已采纳

**背景**：README §4-§5 的完整方案（起点池自扩展、步内中途改选、rollout
可行性查询）会被问题四/五的复杂度卡住。先做简化版闭环，把"技能定义 +
引导训练"打通；中途切换、可行性查询、候选流形推迟到后续阶段回填。

### 简化一：前序技能链式起点池（不支持中途切换）

每轮迭代（一个或几个 update）：

1. 迭代前：每个技能有**候选起点状态集** C（首轮 = READY 等预定义起点）
2. 迭代后：基于最新策略评估，得到**可用起点状态集** U ⊆ C
3. 对 U 中起点执行 rollout，取其执行尾状态构成该技能的**终止状态集** T
4. 下轮迭代前：技能的候选起点 = 其所有前序技能终止状态集的并集
   `C_A ← ∪_{B ∈ pred(A)} T_B`

约定：

- 技能只能从指定前序技能的终止状态出发——不支持步内中途切换；
  中途接管、重锚定、可行性 rollout 全部推迟
- 每个技能需要定义它的**前序技能列表**
- 前序关系 = "允许尝试接续"，不承诺已支持；候选集中保留一部分
  READY 与历史成功起点，防止技能退化导致后继起点断供
- "终止状态"第一版只取执行明确结束的那一帧——取尾几帧会把未完成
  中间态混入，重新引入中途语义
- "可用起点"按当前策略版本理解，非永久标签

### 简化二：只定义执行结果，不设计过程轨迹

- 不人工设计技能的 CPose 过程（动画制作成本高，做不好有误导性）——
  把姿态设计问题变成奖励引导问题
- 结果由**整段评分函数**定义：输入为一次完整执行的 clip（RobotState
  序列），输出单分；一次执行（<0.5s）只给一个整体评分，不分帧
- 三个评分维度：
  1. `score_com` — 质心运动状态与支撑稳定性
  2. `score_step` — 脚是否迈到指定位置
  3. `score_posture` — 终点姿态接近程度与运动过程表现
- 评分实现不限（不要求 CPose），可用 clip 内任意帧信息
- 已落地为 `skills/base.py` v0 契约：`name/instruction/step_budget +
  三个 score_* 方法`；locate/reference/谓词等全部移除

### 奖励传递约定

三维度各成一个 reward channel，clip 末帧结算、actor_weight 全程放开
（`skill_step_mbs` 教训：只在结算帧给 actor_weight 会把准备动作的
学习信号掩掉）。

### 未决与注意

- 合格判定（尾状态能否入终止状态集）仍需少量明确条件，不只看加权
  总分——如"迈到点但已倒"不合格
- 直拳技能评分中必须有明确的打击到位判定，否则"站着不动"也能拿
  高姿态分
- 固定执行时长意味着暂不追求提前完成/速度最优
- 中途切换、可行性查询、自扩展起点池等 README 完整方案能力推迟，
  本简化收敛后再回填

## D4 — 奖励时间分配：γ=λ=1.0 蒙特卡洛 + trim_clip 裁剪结算

**日期**：2026-11-16
**状态**：已定稿（v0）

### 决定

1. **三通道 `gamma=1.0, gae_lambda=1.0`**：整段评分任务用蒙特卡洛
   advantage，`A_t = S − V(s_t)`（REINFORCE-with-baseline 标准形）。
   原 γ=0.99/λ=0.95 下末端稀疏分经 `(γλ)^T` 双重衰减，到第 0 帧
   只剩 ~9%；γ=1 同时让 critic 回归目标变平稳（E[S] 而非逐帧
   衰减的 γ^{T-t}E[S]）。
2. **否决"分数摊到每帧"方案**：摊分（r_t=S/T）本身合法且给出
   "前重后轻"的 credit 形状，但与裁剪组合后是**拖时间发生器**
   ——第 k 帧裁掉只发 S·k/T，早完成反而少拿分，系统性地奖励
   故意延迟完成。
3. **`Skill.trim_clip(clip) -> Optional[int]`**：技能契约新增裁剪
   判定方法，返回"任务已完成"的最早帧数 k；None=未完成/不裁剪。
   - step：摆动脚有效离地→过峰→踝高回落至近地 → 落地+3 帧 settle
   - jab：到位误差 argmin 帧（须 ≤0.16m 才算接近过）+ 5 帧回收余量
4. **裁剪即任务完成**：traj 截到 T_eff，三分在裁剪段上评、结算在
   第 T_eff-1 帧；`is_terminated=True`（对技能 MDP 是真终止，
   非 timeout 截断，V=0 bootstrap 语义正确）。
5. **终止状态回收点同步改为完成帧**：入池快照取 T_eff-1 的
   core_state（之前是 ep 末尾漂移态）。

### 语义与边界

- **速度中性**：早完成与晚完成回报相同——v0 不奖励也不惩罚
  速度；要奖励速度需显式加 `S·decay(t_done)` 类评分项（非本版）。
- **裁剪不终止物理 episode**：episode 跑满步数（observer 照录），
  截断只发生在 build_trajectories 的轨迹层。
- **仍存的退化风险**：非完成保底分（posture≈0.9 站桩）与完成分
  差距过大时，"拒绝尝试"是局部最优——靠 min-score 合格线防污染
  池子，若 step/reach 长期贴零再调分值结构（gating 式打分）。

## D5 — 手臂可脚本化假设的验证实验（arm_takeover）

**日期**：2026-11-17
**状态**：已验证（demo，未进训练管线）
**动机**：脚步+躯干是欠驱动、手臂不是——若手臂动作能用 IK+PD
脚本可靠产生，则可将"全身协调"问题缩小为"下肢在手臂运动时
维持平衡"问题。先验证两个前提：(a) 脚本能实现手臂动作；
(b) 现有平衡策略在手臂被接管后能否保持平衡。

### 决定

1. **关节划分**：臂 6 关节（action[15:21]，shoulder1/2/elbow×2）
   由脚本覆盖；躯干+双腿 15 关节继续由原策略输出。原策略 obs
   含手臂关节位置，能看到接管效果但无法控制。
2. **臂目标直接用归一化关节角指定**（=action 空间值，不经 IK）：
   每臂 `(shoulder1, shoulder2, elbow)`，左右同值即镜像
   （关节轴已按镜像设计）。IK/CPose 路线被放弃——对手向量
   选支不可控（能量最小支选鸡翅构型；肘下扣+颏部高手位又
   超 shoulder1 限位），关节角直接可控且姿势语义直观
   （JOINTSPEC.md 方向约定）。
   - 抱架 `(0.4, -0.3, 0.8)`：s1 pos=夹肘收臂、s2 neg=上臂
     后收锁肘于体侧、elbow pos=屈肘前臂竖护脸
   - 出拳 `(0.4, 0.8, -0.8)`：上臂前抬+肘近全伸直拳
     （e=-0.8 留余量不顶 -1.0 限位）
   - 设计流程：`Pose.render()` 离屏渲染迭代确认后进 rollout
3. **切换语义**：一次性切目标关节角并保持，无插值——PD 自行
   追踪（用户指定）。出拳目标保持 0.3s 后切回抱架。
4. **初始快照**：READY 全身 + 臂关节烘焙为抱架（第 0 帧即抱架）。
5. **序列**：抱架 1.0s → 右拳 0.3s → 抱架 1.0s → 左拳 0.3s →
   抱架 1.0s（72 步 @50ms）。

### 实测结果（s42i_b u01680，确定性 act）

v3 抱架/出拳（关节角直接指定）：

| 场景 | 存活 | max\|pitch\| | max\|roll\| |
|---|---|---|---|
| untouched（对照） | 72/72 | 0.37 | — |
| guard_hold（双臂接管抱架） | 72/72 | 0.43 | 0.23 |
| punch_seq（完整序列） | 72/72 | 0.43 | 0.24 |

（v1 IK 鸡翅臂 0.70 → v2 IK 肘下垂支 0.50 → v3 关节角抱架 0.43；
紧凑抱架使接管成本逼近 untouched 对照）

- **两前提均成立**：脚本臂动作可靠实现；策略全程无倒地。
- **代价**：pitch 峰值翻倍——未经适应训练的接管成本；暗示
  用脚本臂作扰动重训平衡策略有很大适应空间。
- **附带观察**：出拳帧中机器人正处于动态步态单腿抬起相——
  "脚步任意相位出拳"被动成立（双方互不感知，非协调结果）。
- com 漂移 ~0.7m/3.6s 三场景一致——策略固有踱步，非接管所致。

### 未决

- 出拳手实际到位略低于设计目标：臂目标是按 READY 躯干姿态
  离线 IK 的固定关节角，运行中躯干倾斜变化后开环不跟踪。
  若后续要高精度出拳，需在躯干系在线 IK 或直接设定期望偏差。
- 本实验只验证了"接管不摔"。脚本臂作为**训练扰动**的路线
  （脚步训练时随机叠加脚本拳，逼下肢学补偿）尚未实施——
  这是解耦路线的正式下一步，届时再决定扰动强度 curriculum。
