## E. 当前有效路线：从可训练原型到大规模采样框架

### E.1 用户目标与已确认决策

第二轮目标不是证明任意负载下 GPU 都胜过 CPU，而是：**把批量框架建设成面向大规模训练、职责清晰、仿真器可分离、单次训练可使用单机多卡采样的工程体系。** 接口、生命周期、扩展、调试、验证与维护的深度应达到 CPU 框架的层次，不是只把 standup 跑通。

本轮已确认：

| 决策 | 本轮约束 |
|---|---|
| 第一轮成果定位 | 完成限定任务上的可行性、训练 pilot 与跨后端检查；作为重构的参考资产，不等于通用框架已完成 |
| 旧 M7 | 暂停多 seed 训练/端到端倍数正式验收，不记为 R2 已通过 |
| 旧 M8 | 暂停低成本 Agent 独立迁移的正式验收，不记为 R3 已通过；迁移机制本身仍须建设 |
| 对外采样边界 | **保留 `collect(jobs) -> List[Episode]`，保持 Job 顺序及 Episode 语义** |
| 训练侧范围 | 不改 Experiment/Trajectory/GAE/PPOBuffer 的公开数据接口，不引入 Tensor-native learner 通路，不复制 PPO |
| 多卡范围 | **同一训练任务的 1–8 GPU 并行 rollout，单 learner**；不是 8 个独立实验，不做 DDP/分布式更新 |
| 数据驻留 | 原生采样内部使用设备张量与紧凑缓冲；在显式波次/采样块边界导出 Episode，允许 CPU 负责配置、编排与 I/O |
| 语义来源 | CPU 实验、模型、任务参数和指标仍是参考；迁移不静默改变物理、任务或采样分布 |

实施建议边界：首个正式后端为 mujoco-warp + fp32，策略数学继续复用 PyTorch；通用核心不依赖 Humanoid21 或 Warp 私有对象。首轮工程验收围绕现有双机器人任务，不扩张为任意多智能体平台，也不同时实现第二个真实物理后端。FakeBackend 用于独立验证核心契约。

“使用 8 卡”指单次 collect 能把不同 world 分配到 8 张卡，并得到完整、同版本、同契约的 Episodes；不承诺 100% GPU 利用率、线性扩展或训练端到端必然加速。单 learner 与 CPU Episode 接口是本轮主动保留的边界，可能成为之后的瓶颈。

### E.3 目标架构与状态归属

以下为职责设计，不是已存在的新 API 或已冻结的类名。具体签名与目录迁移在 E0/E1 审查后确定。

```text
CPU 实验 / EnvBlueprint / Job / SamplingSpec（权威输入）
                         |
              解析、能力检查、迁移绑定
                         |
       采样执行计划（任务语义与设备部署配置分离）
                         |
        单训练 coordinator：冻结策略版本、分片 Jobs
             |             |             |
          GPU worker 0  GPU worker 1  ... worker 7
             |
       采集器 + 策略执行器 + 设备轨迹缓冲
             |
       BatchRuntime：生命周期、插件、observer、reset
             |
       批量物理后端契约（设备视图 / 受控写 / 推进）
             |
       Warp 驱动 + Humanoid21 模型/控制绑定
                         |
          显式导出、合并、校验 -> List[Episode]
                         |
      现有 build_trajectories / PPOBuffer / GAE / 单 learner
```

| 层 | 拥有的状态与职责 | 不应拥有的内容 |
|---|---|---|
| 模型/任务绑定 | XML/meta、动作与观测 schema、控制映射、任务配置与插件组合 | 通用进程调度、PPO 更新 |
| 物理后端 | 求解器状态、物理资源、设备视图、stream 顺序、状态写入刷新、接触容量与溢出报告 | episode 终止政策、奖励、插件池、策略、Job/Episode |
| runtime | episode/agent 生命周期、活跃 mask、插件状态与随机服务、事件/指标、reset 调度 | 具体 Warp 类型、模型私有索引、训练算法 |
| 插件/observer | 通过声明的视图和写能力计算规则；持久状态交由有明确生命周期的容器管理 | 直接访问 `_wdata`/`_model`/`_torch_views` 等私有后门 |
| 策略执行器 | 冻结行为策略、采样上下文、每 agent 动作与 extras、策略内部状态 | 物理推进、任务奖励 |
| collector | job/episode/帧对应关系、有效性、final observation、设备缓冲与 Episode 导出 | 识别 standup 特定指标、默认替换策略分布 |
| coordinator | 设备与进程、分组分片、版本屏障、背压、结果顺序、错误传播 | 逐 action/physics step 的 CPU 决策 |

实现与设计均要求物理后端可单独使用、runtime 可接 FakeBackend、collector 可替换后端与策略执行器；仅移动文件或保留私有字段耦合不算解耦完成。框架核心不得反向 import humanoid/standup/PPO 实现。明确张量借用与所有权、有效期、写权限和 reset/close 后的失效行为；不能仅用“只读”注释约束所有调用方。

模型相关的 96/21 维可以继续作为 Humanoid21 schema，不能继续写进通用 collector。双机器人是首轮任务范围，不要求本轮扩展全部上下游到任意 agent 数量。

### E.4 设备执行、生命周期与多卡的关键约束

**设备执行分三级，不混为一谈：**

1. 数据常驻：obs/action/reward/termination/轨迹留在设备；采样块完成后统一导出。
2. 无逐步数据依赖 host 决策：避免 CUDA 张量转 bool/item、动态长度索引引起的同步；以固定容量、mask、设备计数和明确错误缓冲表达动态行为。
3. 可捕获执行：在前两级成立后验证 CUDA Graph/编译执行；eager 与捕获共享语义契约。无需强制整个长 rollout 成为一个巨大 graph，也不宣称 Python 本身在 GPU 上运行。

初始化、策略装载、波次边界、按需 debug、显式容量故障检查允许受控同步；必须有可审计边界。HOST/HOST_SLOW 兼容模式独立声明，不能把含慢插件的执行标为完整设备原生。后端库自身的同步或 graph 限制必须实测并列为缺口，不能只扫描本项目 `.cpu()` 就宣称达成。

**生命周期必须先于优化冻结：**

- 物理子步、action step、episode、collect/update 边界分别定义；对齐 CPU 的 hook 时刻与终止优先级。
- 真正 termination、timeout truncation、采样块边界和主动 abandon 分开；停止单 agent 不等于停止整个 world。
- final observation 在 reset 前捕获；不能将下一 episode 的第一帧当作前一条轨迹的 bootstrap。
- episode 结束与 reset 是不同事件；collector 完成一个 job 后不应为了 auto-reset 再运行一次无用的昂贵初始化。
- 插件状态区分 per-step、per-episode、跨 episode、跨 collect；部分 reset 恢复声明的初始值，而非无条件全零。observer/策略状态同样受协议管理。
- 逐物理步反馈不能用事前 force schedule 冒充；schedule 仅适用于事前可确定的输入。依赖最新接触/速度的子步逻辑必须有对应设备执行能力或在解析时拒绝。
- 不支持的状态组合、字段、配置、容量溢出、非有限值必须显式失败，不能漏字段、填零或丢弃异常环境。

**多卡先做同步 on-policy 采样：**

- 一个训练任务、一个 learner、一组冻结的行为策略版本；每卡一个隔离 worker，worker 在卡上批量推进完整 world，同一场两 agent 不拆卡。
- learner 的设备与 rollout 设备列表独立配置；共享卡时分阶段使用并纳入显存预算，不默认额外需要第 9 张卡。
- 区分 global jobs/update、local worlds/GPU、wave 数与有效 agent transitions；改变设备数不能静默改变训练样本预算。
- 按模型/schema/插件布局和可执行策略组合分组；组间分波或分 worker，不把任意异构任务强塞进同一 SIMD batch。
- 随机服务以 run/job/episode/agent/逻辑步/用途域标识派生，不以 rank、局部行号或完成顺序作为样本身份。同后端调度变化不应人为改变随机输入；物理数值不承诺跨 batch/卡数 bit-identical。
- 回收结果按全局 job 身份校验完整、唯一、同版本并恢复输入顺序；padding 不进入统计。PPO 更新前有收集屏障，不做陈旧策略异步训练。
- 对显存、CPU RAM、传输队列和 policy cache 设明确预算及背压；全量 Episode 的 host 占用必须事前估算，超预算在启动前拒绝或要求显式缩小配置。
- 任一卡失败默认使本次 collect 失败；不静默吞掉该卡样本。第一版只承诺 update 边界恢复，不承诺任意 GPU 内核中途恢复或弹性增减卡后逐位复现。

**当前状态（2026-10-02）：W1–W6 已完成。** `binding_registry`（sim_cls→DeviceBinding，io_schema/options 白名单）、`policy_executor`（能力声明检查 + 有界 LRU + state_dict 版本 hash）、`record_store`（schema 驱动预分配 + `output_schema` 校验 + `frame_valid`）、`run_wave`（后端无关，FakeBackend 可测混长波）、`episode_exporter`（向量化导出，`from_buffer_frames` 降为 golden 对照）、`sync_stats` 分类记账均已落地。`collect()` 按同构键分组、返回序=输入序。测试：tests/ 目录 100 项绿（`test_wave_contract` 7 项 + 设备全量 + warp 端到端 5 项）；device collector 冒烟正常。已知残余：`policy_eval_mask` 未贯通 executor（"hold" 模式未接线）、host 导出峰值未单列。详见 [E3_PLAN.md](E3_PLAN.md) 放行条件核对与实现备注。

- collector 不再构造具体后端或指定单一策略类，消费解析后的任务/策略执行器；输出 schema 来自绑定，不写死 96/21 或 standup 指标。
- 用预分配的设备缓冲存 obs/action/extras/observer/终止事件/final observation/有效长度；批量导出，不逐帧创建大批临时字典。
- 先实现明确的同步波次模式，支持该模式内的提前终止与长度差异。采样块切分不改变 episode 语义，未完成片段不能伪装成 timeout；是否加入补位调度在基础正确后单独评审。
- 策略适配保留行为分布、策略版本及 SamplingContext；不以“权重能 load”代替 policy 类型与数学兼容性检查。实现有界策略缓存。
- 原生路径以无逐步 host 数据依赖为目标，通过 profiler 核查同步、动态分配与跨框架 stream 顺序；受限能力只能显式降为兼容路径。

**放行：** 相同数据的 Episode schema/序列化、终止/final_obs、buffer/GAE、log-prob 重放和 Debug 对照通过；CPU collector 不变。报告设备缓冲及 host 导出峰值内存与时间，不承诺整个采样结果零拷贝。

#### E4：单次训练的 1–8 卡 rollout

**当前状态（2026-10-02）：W0–W6 已完成。** `coordinator.py`（JobRef/同构组确定性分片/merge 全量校验）、`worker.py`（spawn + set_device + 内嵌 DeviceRollouter）、`multi_rollouter.py`（all-or-nothing 事务、背压、幂等 close）、`--collector-devices` 接入均已落地。W0 探针：H12 通过、Episode 载荷 0.226MB/ep、pickle 传输无瓶颈。测试：`test_shard_plan` 7 项 + `test_multi_rollouter` 4 项（2 卡契约/padding/worker kill→WorkerLost/幂等 close）全绿；2 卡训练冒烟正常。详见 [E4_PLAN.md](E4_PLAN.md) 放行核对与附录 A。

- 增加 coordinator 与 worker 协议、显式设备列表、策略/任务版本分发与启动自检；CUDA 初始化在 worker 内完成，避免继承不安全的已初始化上下文。
- 静态确定性分片作为首版；同构组内按容量分波，结果按 job 身份重排。动态负载均衡不是首版必要条件。
- 分离 worker 内 GPU 缓冲、host Episode 导出、进程通信和 coordinator 合并；可选择共享内存/紧凑序列化，公共 Episode API 不变。
- 有界队列与背压，worker 异常/超时/退出可定位；统一失败而不是部分成功后继续 PPO。

**放行：** 先 1/2 卡，再在资源获准后 8 卡；验证一个 collect 使用所配置设备、无漏/重/乱序/错版本、padding 不污染、不同分片的随机身份正确；注入单 worker 失败并验证回收/错误传播。固定全局数据量和固定每卡数据量两种规模分别记录，不要求倍数胜过 CPU。单 learner 仍消费原 Episode 列表。

#### E5：把 CPU 实验迁移变成有约束的工程流程

**状态：已完成（E5_PLAN.md）**——`migration_audit.py`（blueprint→单元能力/配置处置表，unknown 键即失败）+ `migration_manifest.py`（证据 manifest + unit_hash 失效追踪，落盘 `migration_manifests/`）；basic_balance 迁移落地：`DeviceDualImbalancePlugin`（首个真实**逐 agent 终止**用例）+ CrossSupport/Posture/HeightPhi 三 observer，13 项同注入态对拍 + e2e collect + 单/双卡冒烟全过。

- 复用权威规则与参数，提供无状态 observer、有状态规则、reset、子步反馈、终止、策略采样等受测试模板。

**放行：** standup 之外的约定能力可以按流程迁移，错误配置/缺失能力/过期版本在执行前被识别；无需独立低成本 Agent 实验，不宣称原 M8 已通过，也不要求一次迁完所有实验。

- 按需捕获指定 job/agent/frame 的真实设备状态与观测奖励；provenance 含逻辑配置、实际后端、模型/代码版本、策略版本和采样身份。
- 区分实际轨迹回放、同后端重跑、CPU 交叉评估；复用现有 dump/viewer/指标，不以 CPU 重算结果覆盖设备原始记录。
- update 边界恢复涵盖协调状态、随机身份、必要持久插件/策略状态和计划版本；恢复应校验拓扑/能力变更，不静默沿用过期验证。
- 覆盖容量超限、非有限状态、设备错误、队列拥塞、worker 退出、资源释放和重复 collect 的内存稳定性。分配预算纳入录制缓冲与 host Episode，不只报 simulator 显存。

**放行：** 可定位并重放一个失败样例；能按既定协议恢复；多次采样无无界缓存增长；异常不被当成空 Episode、零奖励或可忽略的单卡缺失。

#### E7：有依据的执行优化，不重开旧性能竞赛

- 在接口不变的前提下评估 CUDA Graph、固定容量接触聚合、kernel 合并、reset 编排、批量导出和通信优化；每次只改变一类执行机制。
- 正确区分 host 提交时间、GPU 实际执行与端到端时间；编译、启动、reset、policy、physics、observer、记录、导出、合并分别计量。
- 物理 world-substeps = world 数 × action steps × substeps；agent transitions 另算，双机器人不能让同一次 world 物理推进被计数两次。初始化物理步单列。
- 固定模型与任务语义，不以削减接触、子步、输出或放宽容差换取吞吐。硬件拓扑、可用资源和同步路径随结果记录。

**放行：** 容量与开销可解释，有 1/2/8 卡的工程规模记录及已知瓶颈；捕获/优化路径对 eager 语义回归通过。没有“必须比 CPU 快 2×”门槛，也不把吞吐增长直接称为 time-to-quality 改善。

#### E8：综合工程验收与接口稳定

- 对 E0 支持矩阵逐项结算：原生通过、兼容通过、未实现、拒绝、过期；不以 standup 的成功替代通用能力清单。
- 验证 standalone backend、FakeBackend runtime、单卡和多卡 collector、CPU 迁移、短程训练、Debug、checkpoint/故障路径的组合。
- 固定公开 API/配置/schema 版本与弃用路径，整理可实际运行的示例、验证命令、边界与后续扩展方法；旧 host 原型与正式入口不再混淆。
- 保留 CPU 主路径回归。数据语义、生命周期或采样变化触发受影响的 V0–V3 与短训练；是否需要长训练按风险单独确认，不默认再做旧 M7 全矩阵。

**本轮完成标准：** 能通过公开接口为受支持任务装配批量运行时；仿真器与框架在代码依赖和测试上可独立；同一训练任务可用 1–8 卡生成同契约 Episodes；迁移、失败定位、恢复与扩展不再依赖当前作者手工穿透私有实现。

### E.6 工作方式与下一次任务

每次只推进一个清晰工作包：先冻结输入与接口，再写可失败的契约测试，增量实现，运行 CPU/设备相关回归，记录未覆盖项，再提交。不得在同一包里同时重写物理、任务规则、collector 和训练算法。沿用本路线图逐步补充设计资产，不制造一批只有标题的抽象类或未来 CLI。

**下一次从 E0 开始，不直接重写整个框架或启动 8 卡长训练。** 首包产物为：状态/接口/生命周期契约、模块依赖图、首轮支持矩阵、代表性验收案例以及 E1 的可执行拆分。技术选择能由契约和小探针决定的由实现者提出并验证；扩大训练接口、多卡 learner、多机、异步策略或任务范围时再请用户决策。

本次仅审计与更新路线，不改训练代码，不启动/停止/重启现有大 batch 实验，不自动占用 8 卡。运行中的旧实验不再是新路线的前置条件，结果可作为附加证据；停止或清理需另行确认。

## 1. 路线选择与实施边界

### 1.1 本阶段固定的方向

- 当前 CPU MuJoCo 实验是语义参考和转换来源，保留为可运行、可调试的路径。
- 加速路径允许使用另一套原生执行模型，不追求 Python 插件逐行复用。
- 首期主要替换 `Job → Episode` 的采样实现，保留实验接口、Trajectory、PyTorch 策略数学与 PPO。
- 模型、参数、奖励和指标应保留权威来源，必要时允许薄适配和派生代码，不维护两套独立演化的任务规则。
- 兼容执行、原生转换和验证对照是不同能力，必须分别报告。
- 工具与 AI 指南从第一阶段积累，不把“可由低成本 Agent 使用”留到所有代码完成后再补。

### 1.2 首轮不做的事情

不重写整个 PPO 为 JAX，不迁移全部战斗插件，不建设任意 Python 程序的自动转换器，不先做多 GPU，也不要求所有旧插件在设备端原样执行。

不通过更换 XML、删除对手、减少接触或物理子步、改奖励、改初态分布、改变 PPO 更新批量来宣称透明加速。这些变化若确有价值，应另立实验。

### 1.3 三个交付里程碑

- **R1：技术链路闭环（M5）**。对等仿真与原生任务完成，能向原 PPO 提供正确数据，Debug 主要链路可用。此时不宣称效果和加速已经通过。
- **R2：首个训练加速验收（M7）**。standup_floor04 的最终实现通过多 seed 质量、样本效率和端到端性能验收。
- **R3：AI 可迁移体系验收（M8）**。另一个受支持实验可由低成本 Agent 依据指南和工具完成转换；失败和过期状态可检测、可定位。

## 3. M0：冻结参考、支持范围与验收协议

**核心问题：我们要忠实转换的究竟是哪一个实验版本？**

### 工作包

1. 确认主参考 Run、checkpoint、源码 snapshot 和训练配置；保留另一个 Run 作为旁证。
2. 区分历史效果目标与当前公平 A/B 的 CPU 对照版本。审计两者的 PPO、策略、任务和运行参数差异。
3. 复评参考 checkpoint，建立未训练、中期、成熟策略探针；冻结开发用评估集和独立留出集。
4. 梳理目标实验的完整依赖：模型、meta、simulator、reset plugin、observer、reward、SamplingSpec、trajectory 和指标。
5. 列出 simulator 公共契约与任务能力清单，逐项标记首期必需、后续补齐或非目标能力；不将“standup 没用到”当作接口已实现。
6. 分解 CPU 成本：模型初始化、每回合 reset、物理推进、观测奖励、策略推理、进程通信、数据整理、PPO、评估与导出。
7. 冻结误差比较方法、质量非劣效门槛、样本预算、硬件资源和性能计时口径。

### 交付物

- 基线清单：源码/依赖版本、模型与配置标识、参考 Run 和策略、评估种子及参数。
- 任务契约清单：字段、单位、坐标系、采样时刻、随机性、reset 和终止语义。
- 能力矩阵与初始支持范围。
- CPU 复评和性能基线报告；候选门槛经确认后成为正式协议。

### 放行条件

- 历史能力在对应版本可复评，或不可复评原因有明确处理决定。
- CPU 对照与加速候选只允许在已声明的执行维度上不同。
- 没有未解释的任务语义歧义；暂不能确认的能力不能标为受支持。

**暂停条件：** 参考 Run/版本无法确定、主路径本身存在影响验收的缺陷、资源预算无法公平比较。先处理这些问题，不开始完整训练。

## 4. M1：独立验证骨架与 AI 输入规范

**核心问题：在开始大规模转换之前，Agent 能否获得可靠、局部、可重放的反馈？**

### 工作包

1. 建立统一测试样例格式，区分逻辑特征输入、完整仿真状态、固定动作序列和策略评估任务。
2. 提供 CPU 参考数据采集、候选执行、分字段比较和失败样例重放接口。
3. 分离逻辑测试与物理测试：相同特征验证奖励公式，相同完整状态验证仿真推进。
4. 建立结果格式，支持 pass/fail/unsupported/not-run/stale，附比较容差和失败定位。
5. 定义最小来源记录：源代码、模型、配置、后端版本、测试版本及对应产物。
6. 编写第一版 AI 转换输入清单、禁止事项和升级规则；无需此时拥有全部转换模板。
7. 用已知正确样例和刻意构造的错误验证测试工具自身，例如观测维度顺序错误、漏字段、timeout bootstrap 错误和未识别插件。

### 放行条件

- 正确的参考输入能通过；刻意引入的语义错误会失败，不能被默认值掩盖。
- 失败报告至少定位到字段及 episode/agent/frame 或测试样例。
- 同一失败输入可再次执行，不依赖人工复述。
- Agent 无权通过改变 oracle、删样例或放宽阈值来取得通过。

**阶段边界：** 工具验证有限支持范围，不宣称自动证明任意 Python 程序等价。本文描述的是待建设能力，不能把名称当作已有 CLI。

## 5. M2：对等 simulator 与后端可行性

**核心问题：真实模型能否以正确语义运行，并留下有价值的加速空间？**

### 工作包 A：审计和修正现有原型

- 对齐实际 XML、模型参数、meta 和 PD 控制，不沿用旧模型做性能替代。
- 对齐动作、core state、96 维观测、derived 字段、接触、外力、reset 和状态写入刷新。
- 分离设备端数据表示与宿主侧诊断导出，不强制热路径反复转成 NumPy。
- 按公共契约逐项验证；sensor 的空输出、可选渲染等也必须与参考契约对应，不能擅自省略。
- 渲染可通过保存状态和 CPU renderer 适配完成，不要求 GPU 训练热路径提供高速录像；渲染结果与数值来源必须区分。

### 工作包 B：数值和批量对照

- 覆盖站立、躺倒、手脚支撑、起身、多接触、朝向变化、非零速度、外力及状态写入后立即读取。
- 验证一步与 25 子步执行，PD 每个子步更新；区分 qpos/qvel 与 derived/contact 的采样时刻。
- 物理比较采用受控完整状态，记录 warm-start、控制和外力等隐含输入；不能仅比较 CPU 导入的已计算接触力。
- 验证 batch=1、多环境隔离、不同初态、部分状态写入及多步推进。
- 接触按照语义匹配，不依赖存储顺序；容量溢出、无效 contact padding 必须被检测。

### 工作包 C：选型和吞吐探测

- MJX-JAX 是现有原型的起点；MJX-Warp 可作候选，是否引入依赖和是否采用需单独决定。
- FP64 可作误差诊断，不预先要求最终训练必须 FP64；FP32 必须通过同一任务语义验证。
- 用完整模型测编译、显存、稳态物理吞吐和状态导出成本，覆盖目标 512 场及合理的小 batch。
- 以 4090 上的实际结果做选择，不以其他硬件或简化场景的公开倍数代替本项目证据。

### 放行条件

- 冻结的 simulator 必需契约项通过 V0/V1/V2；每项偏差有解释，不存在静默近似。
- 支持范围外的请求明确失败。尚未完成的公共能力保留为缺口，不宣称完整 simulator 对等。
- 选择至少一个语义可接受且有性能潜力的后端/精度配置。
- 不稳定状态、NaN 和接触容量问题可定位，不能靠过滤失败环境伪造成功。

**暂停条件：** 真模型不支持、关键接触语义无法保留，或物理性能上限不足以支持整体收益。此时先调整后端或执行实现，不通过修改任务过关。

## 6. M3：原生批量运行时、插件体系与兼容边界

**核心问题：怎样让转换后的任务逻辑可靠地在设备上执行，而不是给旧 framework 加一个 batch 维度？**

### 工作包

1. 设计最小原生契约：静态配置、显式插件状态、随机状态、只读 observer 输出和允许的物理修改。
2. 定义 reset、action-step、physics-step、episode-end 的 hook 顺序、权限和数据可见性。
3. 明确 per-env 与 per-agent 终止、timeout、active mask、终止后的状态处理以及 reset 行为。
4. 高频插件进入设备执行；日志、导出和少量录像保留在宿主侧。
5. 建立旧插件/blueprint 到原生实现的显式注册与能力检查，不做模糊猜测映射。
6. 提供有限的宿主执行适配，用于低频插件和对照；输出中标记模式与潜在性能代价。
7. 提供无状态 observer、有状态插件、物理步施力和 reset 的最小模板及示例测试。

### 放行条件

- 用轻量测试后端验证生命周期，不必每次依赖真实 MJX 编译。
- hook 顺序、权限、reset 状态清理和环境间隔离有自动化测试。
- 逐物理步修改发生在正确子步，不能由事后 history 模拟。
- per-agent 结束不会误当作整场结束；部分 reset 不影响未重置环境。
- 原生/兼容/待转换/不支持四种状态明确；未识别插件和配置启动时拒绝。

**范围控制：** standup 首个 collector 可以只使用同步固定长度模式；运行时契约需能表达终止差异，但异步补充新 episodes 的吞吐调度不作为本阶段必需功能。

## 7. M4：standup 任务转换与环境级验收

**核心问题：转换后是否仍是同一个起身任务？**

### 工作包

- 转换当前 observation、RandomFallenStatePlugin、StandingBalance4StageRewarder 和 timeout。
- 保留双方处于同一物理环境、各自贡献 trajectory 的语义。
- 阈值、公式、控制与任务参数尽量引用共享源；仅执行方式派生。
- 先用 CPU 生成的相同初态验证后续逻辑，再完成设备端 reset，分开定位误差。
- 明确初始化停止条件、保留速度和初态写入的语义；正式训练不能悄悄换成有限状态库。
- 覆盖各阶段和门槛附近样例，单独验证接触 body 去重、力阈值、承重比例及 potential。
- 用未训练、中期和成熟 CPU 策略做固定策略交叉评估，并检查 batch 大小变化的影响。
- 把这次转换形成可复用示例：输入清单、转换规则、代码模式、失败记录和通过证据。

### 放行条件

- V0–V2 的目标任务测试通过，V3 达到冻结的固定策略对照门槛。
- 相同状态特征上的奖励与 observer 一致；物理误差与逻辑错误分开报告。
- 初态分布的高度、朝向、关节、速度、接触和阶段没有无法解释的系统性偏移。
- 所有训练需要的字段显式存在，不以零值或空输出掩盖缺失。
- 对关键阈值附近的分歧有统计和判定，不能只汇报平均误差。

**暂停条件：** 固定旧策略在 MJX 上系统性退化，或 reset/reward 对照失败。先修环境，不能期望 PPO 自动适应错误实现后再宣称等价。

## 8. M5：Rollout、PPO 与 Debug 的技术闭环

**核心问题：原训练和分析体系能否消费加速路径的数据，而且消费的是同一个训练问题？**

### 工作包 A：采样与训练连接

- 在训练框架中增加 collector 选择，不复制 trainer 或实验指标实现。
- 目标实验首版保留 512 episodes/update、200 action steps、双机器人采样和原更新参数。
- 使用现有 TruncatedNormalPolicy 的 tensor 数学做批量推理；处理设备交换、随机流和策略版本。
- 输出同契约 Episodes，保持 Jobs 顺序、options、observer 字段和 SamplingContext。
- 用相同 Episodes 验证 build_trajectories、PPOBuffer、GAE、return、bootstrap 与更新结果，先排除数据适配差异。
- 验证策略在采样期间冻结，采样 log-prob 与更新前重算 log-prob 对齐；不混入过期策略数据。

### 工作包 B：Debug 与恢复

- 日志记录逻辑任务和实际后端配置；保留现有 stats/exp/eval 等指标含义。
- 对接 dump 的 Episode、trajectory、buffer 和 update 数据，保留来源映射。
- 验证 metrics/summary、GAE/advantage、timeline、梯度诊断和保存观测上的 policy-drift 分析。
- 提供按需物理状态捕获及渲染适配，明确实际采样回放、同后端重跑与 CPU 跨后端评估的区别。
- 初期优先保留 CPU evaluator；MJX evaluator 作为额外交叉检查，避免自我验收。
- 在 update 边界支持 checkpoint/resume，保存必要的随机和后端配置；不默认承诺任意中途暂停或跨后端 bit-identical 恢复。

### 放行条件：R1

- 每完整 update 有 512 场、1024 条 agent trajectories、204,800 个有效 agent transitions，无漏帧/重复/跨回合拼接。
- final observation 来自 reset 前的最后后继状态，timeout 保留 bootstrap。
- 相同数据上的训练处理对照通过，短程 smoke 和恢复通过，无采样分布漂移。
- 主要 Debug 数据分析可用，真实轨迹查看有后端来源标识；不能把 CPU 重跑当成 MJX 原轨迹。
- 完整 collector 有性能分解，确认 GPU 物理收益没有被逐步宿主回传和 Python 循环完全抵消。
- CPU 原路径相关回归测试通过，加速路径可显式选择也可不使用。

R1 只证明技术闭环，不代表学会任务或达到加速目标。

## 9. M6：训练 pilot 与性能收敛

**核心问题：候选路径能否学习，真正的瓶颈在哪里？**

### 工作包

1. 从相同初始化协议开始 CPU/MJX 单 seed pilot；分段检查后再推进到预定完整预算。
2. 比较 stage/potential 分布、成功率、末帧能力、KL、uncertainty、confidence 和样本效率。
3. 将质量偏差按 reset、物理、观测奖励、采样分布、数据时序、训练处理分类诊断。
4. 同时测完整 wall-clock，区分冷启动、稳态、评估更新和非评估更新。
5. 依据 profiling 优化：接触聚合、观测奖励、设备交换、批量推理、JIT 重建、reset 和 Episode/Buffer 转换。
6. 每次只引入一类主要变化，重新运行受影响的 V0–V3 和短程训练检查。

### 放行条件

- pilot 能达到预设的学习进展和最终质量候选门槛，无未解释的系统性偏差。
- 有完整成本分解，存在可实测的端到端收益，而不是仅 raw physics SPS 提升。
- 选定一个最终候选并冻结代码、后端、精度、batch 调度和训练配置，准备正式验收。

**暂停条件：** 效果只能通过改任务或另调一套 PPO 才成立；或加速只有在大幅改变原更新批量后成立。可以另设优化实验，但不能把它算作本轮等价迁移成功。

JAX 策略重写、JAX trainer、多 GPU 仅在 profiling 和后续需求支持时另立工作包，不作为掩盖当前瓶颈的默认方案。

## 10. M7：多 seed 训练与加速正式验收

**核心问题：最终实现是否在可接受波动内达到同等能力，并确实更快？**

### 验收矩阵

| 策略来源 | 冻结 CPU 环境 | MJX 环境 |
|---|---|---|
| CPU 训练 | 参考质量 | 后端差异检查 |
| MJX 训练 | 主验收质量 | 训练域表现检查 |

### 工作包

- CPU/MJX 使用相同协议，至少 3 个训练 seeds，正式稳定性结论优先 5 个；预算在 M0 冻结。
- 在独立留出初态/种子集上评估最终版本，建议从 512 场 episodes 起步，按统计精度需求扩充。
- 比较预设末段窗口，不挑单个最高点；分开报告曾站起、最终站立、final_pot 和持续站立。
- 计算稳定达到目标能力所需的 agent transitions 和 wall-clock；未达标 Run 显式记录，不能丢弃。
- 报告按训练 seed 的结果和总体不确定性，同场双 agent 按 episode 处理相关性。
- 计入 reset、推理、转换、PPO、评估和导出，单独报告启动/编译成本及资源预算。

### 放行条件：R2

- 满足 M0 冻结的质量非劣效、样本效率和端到端性能门槛。
- MJX 策略在 CPU evaluator 上也通过，不依赖后端特有的异常接触或数值漏洞。
- 最终被验收版本就是性能优化后的版本，没有拿旧版本效果证明新版本正确。
- 分别记录“转换完成、语义通过、训练通过、加速通过”，所有对应证据可追溯。

用户已确认：成功率非劣效容忍 2 个百分点、final_pot 非劣效容忍 0.02、达到相同能力最多使用 1.25 倍样本量、端到端加速至少 2×。详见 M0 §5.1。具体统计与资源协议须在正式运行前冻结；R2 不能在结果出来后通过放宽门槛获得。

## 11. M8：AI 迁移体系的独立验收与受控扩展

**核心问题：离开原作者和当前会话，低成本 Agent 是否真的能完成转换？**

### 工作包 A：把首个案例变成可使用的机制

- 整理 AI 入口说明：读什么、生成什么、哪些不能改、运行哪些现有工具、什么情况必须停止。
- 提供稳定模板、支持矩阵、结构化测试报告、失败样例和重放方法。
- 增加转换 manifest 和失效检查：源代码、模型、配置或后端版本变化后，旧验证结果标为 stale。
- 规范部分成功和失败输出，不能把未运行的训练/性能验收显示为通过。
- 将工具能力建设在真实实现上，不用“待编写命令”充当可交付接口。

### 工作包 B：独立迁移试验

- 选择第二个现有 CPU 实验，具体对象在 R1 后结合支持矩阵确认；应包含至少一种 standup 未充分覆盖的差异。
- 在交给 Agent 前冻结任务范围、工具和验收标准，保留尚未提供 MJX 答案的任务部分。
- 让一个未参与实现、仅得到项目文档与工具的低成本 Agent 执行转换；届时另行授权和安排，不以本路线图自动启动 Agent。
- 记录首次通过率、修复轮次、人工介入原因、token/API 成本、新增代码量与转换后的验证层级。
- 人工补充解释暴露的是指南或工具缺口，应修复资产后重新试验，不能仅在聊天中教会某一个 Agent。

### 工作包 C：负例与维护试验

- 注入不支持插件，要求转换前明确拒绝或升级，而非静默忽略。
- 修改主路径奖励参数或依赖代码，要求原转换被判定为过期。
- 注入可检测错误，例如漏 observer、错误 bootstrap、遗漏逐物理步 hook，要求工具定位失败。
- 按实验需求扩展部分 reset、提前终止、物理步扰动、多奖励、对手或课程；每种能力单独验收。

### 放行条件：R3

- 受支持的新案例可主要依赖指南和工具完成，无需人工重写核心转换代码。
- 通过转换的案例达到预定验收层级；若只完成语义验证，不能标为已经训练加速成功。
- 不支持、错误和过期案例不会被误报成功。
- “低成本”的预算、允许人工介入范围和目标通过率在试验前约定，以实测评价，不凭主观判断。
- 形成可重复的迁移机制，而不是只有一份手工写好的 standup MJX 代码。

## 13. 风险与回退规则

| 风险 | 最早检查阶段 | 处理方式 |
|---|---|---|
| 现有 MJX 与 CPU 模型、观测已漂移 | M0/M2 | 按冻结代码重建契约，不直接接 PPO 试运气 |
| 接触力差异影响四阶段奖励 | M2/M4 | 分开检查求解、接触分类和奖励公式 |
| NumPy 往返、Python 循环吞掉 GPU 收益 | M2/M5 | 测真实热路径，逐项迁到设备端 |
| FP64 在目标硬件成本过高 | M2 | 诊断精度与训练精度分开验证 |
| reset 改变任务分布 | M4 | 相同初态与原生 reset 分两步验收 |
| rollout 策略与 PPO log-prob 不一致 | M5 | 相同权重/ctx 对照，检查策略冻结与数据来源 |
| Debug 重演的轨迹不是训练轨迹 | M5 | 保存实际状态，明确重跑与跨后端评估区别 |
| 单 seed 偶然成功 | M7 | 多 seed、留出评估和预设窗口 |
| Agent 只在作者提示下才能完成 | M8 | 独立试验，反馈沉淀到工具与规范 |
| 主路径变更后加速实现静默过期 | M8 | 依赖来源记录和 stale 检测 |

未过关时保留已完成的局部能力及失败证据，但不升级成功标签。主路径始终可用；后端切换不得污染原训练数据、checkpoint 或历史 Run。

## 14. 每个实施工作包的完成标准

后续每次会话应只领取清晰的工作包，并交代：

1. 所属阶段、目标和明确不做的事项。
2. 冻结的输入版本、支持能力与改动范围。
3. 正确性测试、负例和预期失败模式。
4. 实际通过的验证层级，以及未执行/失败/不支持项。
5. 性能或训练结果的适用条件，不能将局部结果外推为总体结论。
6. 来源记录和需要更新的指南/模板。
7. 对 CPU 主路径的回归检查，以及代码提交信息。

不要把“代码已写完”“smoke 没报错”或“某次 reward 上升”作为阶段完成的唯一依据。无需为了赶阶段而删除阻塞项或放宽门槛。

## 15. 第一轮启动时的实施建议（历史，非当前入口）

第一轮启动时计划先交付一份可执行的基线与契约包，而不是先补完整 BatchRuntime；当前下一步见 E.6：

- 确认主参考 Run：总纲列出的两个完整 Run 仅为候选，不能擅自当作用户已经选定。
- 确定当前 CPU 对照的代码/依赖版本和资源预算。
- 完成目标实验依赖与 simulator 能力清单，标记现有 MJX 缺口。
